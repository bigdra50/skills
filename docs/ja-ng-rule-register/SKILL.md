# 日本語の指摘を検査ルールへ落とす

「この言い回しはやめてほしい」という一度きりの指摘を、次から機械が拾う状態にする手順。
語を辞書へ足す作業そのものは 1 分で終わる。
時間をかけるのは、その語を本当に足してよいかを実測で確かめる部分。

## 辞書の正本

規範の辞書は dotfiles の `.claude/prh-writing-style.yml` に置いてある。
検査の実行経路は `<dotfiles>/scripts/md-lint.sh` ひとつで、mise task・CI・Claude Code の hook がすべてここを通る。
新しい検査エンジンを別に作らない。
textlint で表現できる指摘は必ず辞書へ入れ、表現できない指摘だけを別の仕組みへ回す。

散文の規範そのものは `.claude/rules/writing-style.md` にある。
辞書は規範のうち静的に検査できる部分を写したものなので、片方だけ直すと両者がずれる。

## 手順

### 1. 指摘を 1 文に固定する

「AI っぽい」という感想のままでは登録できない。
指摘のもとになった文をそのまま持ってきて、どの語がどう働いて文を悪くしているかを言葉にする。
ここで語を特定できないなら、それは辞書ではなく規範文書に書く指摘。

### 2. パターンを狭く書く

prh の `pattern` は正規表現。
語の一部にしか一致しない広いパターンを書くと、無関係な複合語まで拾う。
迷ったら前後の助詞や活用まで含めて絞る。

### 3. 既存コーパスへ当てて数える

登録前に必ず実行する。
この手順を飛ばした登録は認めない。

```bash
# 設定リポジトリと技術ノートの両方で、候補語のヒット数を数える
cd <dotfiles>     && git grep -n '<候補語>' -- '*.md' | wc -l
cd <notes-repo>   && git grep -n '<候補語>' -- '*.md' | wc -l
```

数えたらヒット行を全部読む。
サンプリングで済ませると、正当な用法の塊を見落として誤検知だらけのルールが残る。

### 4. 実測で採否を決める

| 実測 | 判断 |
| --- | --- |
| ヒット 0 件 | 採用してよい。将来の誤検知を防ぐためパターンは狭いまま保つ |
| 数件で、すべて直すべき文 | 採用する。同じ変更で既存の文も直す |
| 多数だが、すべて直すべき文 | 先にまとめて直し、直し終えてから採用する |
| 正当な用法が混ざる | 採用しない。文脈判断は人と LLM の層に残す |

正当な用法が 1 件でも混ざるなら、その語は辞書に向かない。
辞書は文脈を見ないので、混在は必ず誤検知として現れる。

### 5. グッドパターンをセットで書く

`expected` に直す方針、`prh` に差し戻しメッセージを書く。
メッセージには「なぜ悪いか」と「こう書く」の両方を入れる。
悪い理由だけ書くと、語を別の語へ置き換えて終わる直し方を誘発する。

```yaml
- pattern: /重要なのは/
  expected: "主張をそのまま書く"
  prh: "「重要なのは〜」は主張の予告。枠を外して主張を直接書く。"
```

値に `: ` を含むと YAML のマッピングと解釈されるため、`expected` と `prh` は必ずダブルクォートで囲む。
`textlint --fix` は走らせない。
`expected` はリライト方針のヒントであって置換文字列ではないので、自動修正すると文章が壊れる。

### 6. 登録して測り直す

辞書へ足したら `bash <dotfiles>/scripts/md-lint.sh` を全体へかけ、増えた指摘件数が実測どおりかを確かめる。
想定より多いならパターンが広すぎる。
規範文書の側にも同じ内容を書き、辞書と規範がずれないようにする。

## 較正の実例

「効く」を辞書へ入れたいという要望から始めた較正が分かりやすい。
設定リポジトリ 55 ファイルと技術ノート 184 ファイルへ当てた結果は次のとおり。

<!-- 計測例として候補語そのものを引用しているため、この表だけ検査から外す。
     ルール名を指定した除外は 2 インスタンス目に効かないので、名前なしで囲む -->
<!-- textlint-disable -->
| 候補語 | ヒット | 内訳 | 判断 |
| --- | --- | --- | --- |
| 効く | 48 件 | 全件が「作用する」「有効である」の正当な用法 | 不採用 |
| ではなく | 291 件 | 実質のある対比と空虚な対比が混在し、正規表現で切り分けられない | 不採用 |
| 必要に応じて | 4 件 | 少数で、個別に読んで判断できる | 採用可 |
<!-- textlint-enable -->

「効く」は看板に掲げたくなる語だが、実測すると 48 件すべてが正当だった。
「dotfiles 以外のプロジェクトでも効く」「人間向け設計がそのまま AI にも効く」は、どちらも作用を述べていて空の強調ではない。
数えずに採用していれば、48 件の誤検知を毎回浴びて検査そのものが無視される状態になっていた。

「ではなく」も同じ理由で落ちる。
「実装ではなく振る舞いをテストする」は対比に実質があり、「A ではなく B」という空の枕とは別物。
両者を隔てるのは文脈だけなので、辞書ではなく規範文書と LLM 層の担当になる。

## 入れない語の見分け

次のどれかに当てはまる語は辞書へ入れない。

- 一般語としての用法が広い。「効く」「動く」「見る」など、日常語がそのまま技術的な意味を持つもの
- 対比や条件の構文の一部。「ではなく」「場合は」など、構文として正当な出現が大半を占めるもの
- 良し悪しが文脈で反転する。同じ語が、ある文では空虚で別の文では必要なもの

これらは規範文書に書いて、書き手と LLM に判断させる。
辞書の役目は、文脈を見なくても常に悪いと言い切れる語だけを捕まえること。

## 判断に迷う語の置き場

正当な用法が少数混ざるだけの語は、正本の辞書から外して別の辞書へ回す。
業務文書や提案書でだけ問題になる語がここに入る。

分けた辞書は `severity` を `warning` にして、検査を落とさない形で鳴らす。

```json
{
  "rules": {
    "prh": {
      "severity": "warning",
      "rulePaths": ["./prh-business.yml"]
    }
  }
}
```

textlint は同じ設定ファイルへ `prh` を二重に書けない。
error の辞書と warning の辞書を併用するなら、設定ファイルごと分けて別経路で走らせる。

## メッセージの書き方

差し戻しメッセージは、語の置換ではなく文の書き直しを促す形にする。

<!-- textlint-disable prh -->

| 書かない | 書く |
| --- | --- |
| 「非常に」は使わない | 「非常に」は中身のない強調。削っても主張は変わらないことが多い |
| 「掘り下げる」は禁止語 | 「掘り下げる」は動作の中身を示さない動詞。実際の動作で言い換える |

<!-- textlint-enable prh -->

上の表は辞書が検出する語をそのまま引用しているため、検査を局所的に外してある。

検出された語は、文の組み立てが崩れている合図として表に出てくる。
語を類語へ差し替えると、崩れたまま検査だけ通る文が残る。
メッセージには、その文で何を書くべきだったかを書く。

## 由来

この手順は、日本語の言い回しを Hooks で検査するという公開記事の仕様から起こした推定実装。
