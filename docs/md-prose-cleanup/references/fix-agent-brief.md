# 修正エージェントへ渡す指示のひな形

並列で修正させるときに各エージェントへ渡す。
`<...>` を実際の値に置き換えて使う。

## ひな形

```
対象リポジトリ: <target-repo>
検査ツール: <dotfiles>

## 検査コマンド（これが唯一の正解判定）
cd <dotfiles> && bash scripts/md-lint.sh <対象ファイルの絶対パス>...

出力が空になれば完了。対象は必ず <target-repo> 配下の絶対パスで渡すこと。

## 守る文章規範（<dotfiles>/.claude/rules/writing-style.md が正本。最初に必ず読むこと）
- 句点の後で改行する（一文一行）。箇条書きの各項目も1行にする
- 箇条書きの1項目の文末に句点を付けない
- em ダッシュで語句を接続しない
- ラベルと説明を分けたいときはネストを使う（親にラベル、子に補足）
- コロンで終わる文の直後に箇条書きを置かない
- 冗長な修飾語・誇張表現・定型句を避ける

## 厳守事項
1. 指摘された箇所だけを直す。関係のない文を書き換えない。構成を変えない
2. 技術的な意味を絶対に変えない。数値・単位・型番・コマンド・パス・URL・Issue 番号・
   日付・固有名詞・ハイパーパラメータ・評価スコアは1文字も落とさない
3. コードブロックとテーブルの中身は触らない。テーブル外の地の文は対象
4. 担当ファイル以外に触れない
5. git commit / git add / git push をしない
6. 直したら md-lint を実行し、出力が空になるまで繰り返す

## 直し方
- 一文一行: 句点の後で改行するだけ。文そのものは変えない
- 箇条書き末尾の句点: 「。」を消すだけ。項目内に複数文があるなら1行に保ったまま最後だけ消す
- em ダッシュ: 「ラベル — 説明」→「ラベル: 説明」。地の文の挿入句なら文を分けるか括弧にする
- 太字とコロンの組み合わせ: 太字をやめるか、ラベルを親項目にして説明を子項目にネストする。
  情報は落とさない
- コロン終わりの導入文: 「対応は次のとおり。」のような普通の文にする。箇条書きは消さない
- 助詞の重複: 文を分けるか語順を変える
- 長すぎる文: 意味の切れ目で分ける。内容は落とさない
- 漢字の連続: 読点を入れるか助詞を足す。用語そのものは変えない
- 括弧の対応ずれ: 本物のバグの可能性が高い。閉じ括弧の欠落か全角半角の混在。
  前後を読んで正しく閉じる。文が途中で切れている場合は勝手に補完せず報告する
- 誇張表現: 具体的な条件や数値があるならそれを書く。無ければ表現を弱める。
  技術的な事実として正確なら残してよい。その場合は報告に理由を書く

## 報告
何件直したか、各指摘をどう直したかを返す。
内容そのものの問題（括弧の欠落、文の途中切れ、数値の矛盾）を見つけたら必ず列挙する。
判断に迷って直さなかった指摘があれば理由も書く。
```

## レビュー段に渡す指示

修正の後に必ず置く。
目視ではなく機械照合で確認させる。

```
編集された md の差分を読み、技術的な意味が変わっていないかを確認する。

HEAD 版と作業版を突き合わせて次を集合比較する。
- 数値トークン
- インラインコードとコードフェンスの本文
- Markdown リンク先
- テーブル行
- 箇条書き・見出し・画像の個数
- 否定語と数量語の出現数

見出しを改名した場合は、アンカー到達性を HEAD 版と現行版の両方で計算して比較する。
壊れたリンクの集合が前後で一致していれば、今回の編集による破壊は無い。

意味が変わった箇所を見つけたら自分で直す。ただし lint の指摘を復活させないこと。
```

## 程度語を削るときの注意

<!-- 規範が禁止語そのものを例として引用しているため除外する -->
<!-- textlint-disable @textlint-ja/ai-writing/no-ai-hype-expressions -->
誇張表現のルールは「完全に」「大幅に」を削らせるが、単に削ると程度の情報が落ちる。
直後に実測値が併記されているなら削ってよい。
併記が無いなら、辞書に載っていない語で程度を残す。
<!-- textlint-enable @textlint-ja/ai-writing/no-ai-hype-expressions -->

```
割り引く必要がある          → 大きく割り引く必要がある
cube から外れた位置で空振り → cube から大きく外れた位置で空振り
```
