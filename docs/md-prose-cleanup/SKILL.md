# Markdown 散文の一括メンテナンス

既存リポジトリの Markdown へ文体規範をまとめて適用する手順。
1 ファイルの推敲ではなく、数十から数百ファイルを一度に扱うことを想定している。

前提として、dotfiles 側に textlint 環境が入っていること。
実行経路は `<dotfiles>/scripts/md-lint.sh` に集約されている。
mise task・CI・Claude Code の hook はすべてここを通るため、手元と CI で結果が食い違わない。

## 手順

### 1. 実測する

推測で設定を決めない。
まず現状の指摘数をルール別とディレクトリ別に集計する。

```bash
python3 <skill>/scripts/survey.py <target-repo>
```

この集計が後続のすべての判断材料になる。
件数を見ずにルールを選ぶと、鳴りっぱなしで使われない設定ができあがる。

### 2. 適用範囲を決める

指摘は 2 種類に分かれる。
実測すると、大半は LLM 向けのプロンプト文書に集中する。

エージェント向けの文書（`.claude/commands/`、`.apm/agents/`、`AGENTS.md`、`SKILL.md`）は
`- **ラベル**: 説明` のような機械的な体裁を意図的に使う。
人間向け散文の規範を当てても直す価値がない。
`.textlintignore` で外すか、対象に含めるかをユーザーに確認する。

ここで必ず聞くこと。
残った指摘が「そのリポジトリの流儀」なのか「単に未修正」なのかは、書き手にしか判断できない。
流儀ならルールを外し、未修正なら直す。

### 3. ラベル衝突を検査する

`Phase N` `ステップ N` `フェーズ N` のような番号ラベルを grep し、
**同じ番号が何系統で使われているか**を数える。

```bash
cd <target-repo>
for n in $(seq 0 9); do
  echo "Phase $n: $(git grep -l "Phase[ 　]*$n" -- '*.md' | tr '\n' ' ')"
done
```

1 つの番号が複数の無関係な体系を指していたら、それが最も価値の高い発見になる。
番号は定義表へのポインタでしかなく、内容を持たない。
置き換えは「ポインタを参照先の中身で置き換える」ことになる。

恒久的な識別子が要る場合だけ、既にあるもの（Issue 番号）を使う。
新しい番号体系を作ると、いずれ同じ衝突が起きる。

上流プロジェクトの呼称は改名しない。
改名すると上流を参照できなくなるため、理由を書いたコメント付きで `textlint-disable` に囲む。

### 4. 並列で直す

指摘件数でバッチに分け、1 バッチあたり 100 件前後を目安にする。
各エージェントに渡す指示は `references/fix-agent-brief.md` を使う。

バッチはファイル単位で切る。
同じファイルを 2 つのエージェントが編集すると衝突する。

最後に必ずレビュー段を置く。
レビューは目視ではなく機械照合で行う。
照合対象は数値トークン、コードフェンス本文、テーブル行、リンク先、箇条書きの項目数、アンカー到達性。

見出しに含まれる記号を書き換えるとアンカーが変わる。
改名の前に `](#...)` 形式の参照がリポジトリ全体に無いことを確認する。

### 5. 内容の欠陥を分離する

文体を直す過程で、内容そのものの欠陥が必ず出てくる。
リンク切れ、数値の矛盾、撤回済みの主張の残存、実装に追随していない参照。

直してよいのは**リポジトリ内の証拠で正解が一意に決まるものだけ**。

| 直す | 直さない |
| --- | --- |
| 表の行を数えれば件数が確定する | 2 つの数値のどちらが正しいか決まらない |
| grep で正しいパスが一意に決まる | どの文書を指すはずだったか履歴からも不明 |
| git 履歴で機械置換の産物と確認できる | 測定方法や実験条件の解釈が要る |

決まらないものは `CONTENT-ISSUES.md` にまとめる。
構成は「問題 / 対応（チェックリスト）/ 補足（確定した事実）」の 3 部。
各項目に `file:line`、矛盾の内容、候補、著者に聞くことを書く。
影響の大きさで並べる。

推測で数値を書き換えるのが最悪の失敗になる。

## やってはいけないこと

`textlint --fix` は走らせない。
prh 辞書の `expected` はリライト方針のヒントであって置換文字列ではないため、自動修正すると文章が壊れる。

コードブロックとテーブルの中身は触らない。
例外は、値を持たないプレースホルダ記号と、見出しを写しただけの図のラベル。

数値、単位、型番、コマンド、パス、URL、Issue 番号、ハイパーパラメータ、評価スコアは根拠なく変えない。
